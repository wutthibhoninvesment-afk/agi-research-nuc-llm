# Deploy Helper

## When to use (triggers)
- User asks to deploy, ship, release, push to prod/production, roll out a
  change, or run a deploy/release script.
- User asks how to trigger or check a CI/CD deploy pipeline.
- User asks about rolling back a bad deploy.

**When NOT to use:** starting a local dev server, editing CI config that
doesn't ship anything (linting, test-only workflows), or general
infrastructure work with no deploy in scope.

## Steps
1. **Confirm the target environment out loud** (staging vs production) —
   do not assume; ask if it's ambiguous from context.
2. **Check git state is clean and on the intended branch**:
   ```bash
   git status --short
   git branch --show-current
   ```
   Uncommitted changes or the wrong branch means stop and confirm with the
   user before proceeding — production deploys are hard to reverse.
3. **Run pre-deploy checks** (tests/build) if the project has them —
   don't deploy on a red build.
4. **Run the deploy command.**
   > _Placeholder — replace this with the project's actual deploy
   > invocation (e.g. `./deploy.sh prod`, `vercel --prod`,
   > `kubectl rollout`, a CI trigger). This skill has no visibility into
   > your deploy tooling yet; leaving this generic is what makes a skill
   > look followed but do nothing real._
5. **Verify the deploy succeeded** — hit a health-check endpoint, check
   the pipeline's status, or tail logs, per what step 4 exposes.
6. **State the rollback command before you need it**, not after — know
   how to undo step 4 before running it.

## Pitfalls
- **Deploying with uncommitted changes silently included** — `git status`
  before every deploy; an untracked file or stray edit ships to
  production without ever being reviewed.
- **Deploying from the wrong branch** — a feature branch or stale local
  branch can look identical to `main` in a terminal prompt.
- **Running the deploy command without a known rollback path** —
  irreversible by the time something breaks; confirm the rollback command
  works *before* the forward deploy, not after.
- **Treating staging and production deploy commands as interchangeable**
  — confirm the target flag/environment variable every time; a copy-paste
  from a staging runbook onto prod is a common source of incidents.

## Verification
- [ ] `git status --short` is empty and `git branch --show-current` is
      the expected branch before running step 4.
- [ ] Pre-deploy checks (tests/build) passed.
- [ ] Post-deploy health check/smoke test passed.
- [ ] Rollback command is known and was stated before the deploy ran.
