# Re-pin a generated oracle by differential, never by "what it prints now"

## The situation

A file opens:

```python
"""GENERATED by harness/swe/killers.py — do not edit by hand."""
```

and every test in it is one line of arithmetic against a recorded value:

```python
def test_kill_values_py_139_const_121():
    """mutant values.py:139:const#121: 12 -> 13 (line 139) — mutant gave …"""
    src = 'let v1 = @{a: [at("let a", "+"), zz, "ab"], c: …}\n'
    assert run(src) == {'kind': 'ok', 'vals': {'v1': '@{a: [miss, miss, "ab"], …}'}}
```

You make a deliberate change. Eleven of these go red. Now:

* **regenerating is not available.** The generator needs the mutation JSONs
  those killers came from, or the recorded HTTP session, or the fixture
  database — and nobody kept them.
* **the expectation is the entire test.** There is no separate statement of
  what it was catching. Paste in whatever the code prints today and it goes
  green, still looks like a regression pin, and may no longer distinguish
  anything at all. Nothing in the repo would ever say so.
* **`-u` is the documented fix**, and `-u` is exactly the operation above.

The reflex — "the change is intended, so update the snapshots" — is the same
keystroke whether the diff is your change or your change plus a regression it
caused. That is the problem to solve, and it is solvable without the
generator.

## When to use this

Reach for it the moment a change of yours turns a machine-written expectation
red. Concretely:

- a snapshot / approval / golden / cassette file goes red and the tool's
  advice is `-u`, `--update-snapshots`, `--snapshot-update`, `ACCEPT=1`, or
  "delete the `.approved` file and re-run";
- the file's header says GENERATED or *do not edit by hand*, and the
  generator's inputs (a mutation report, a recorded HTTP session, a fixture
  database, a corpus) are not in the repo;
- the expectation IS the assertion — no sibling file, docstring or ticket
  records what the test was catching;
- the pin's provenance is a coordinate that decays: a line number, a mutant
  id, a commit hash, a recording date, a row id;
- a reviewer is about to approve a 40-file snapshot diff on the strength of
  "the change was intended".

Do NOT reach for it when the assertion is hand-written and you can simply
edit it and argue for the new value in review — that is a normal change, and
wrapping it in machinery buys nothing.

## The obligation you can actually discharge

You usually cannot re-prove *this test still catches the thing it was built
to catch*. What you CAN prove, exactly:

> The difference between the old pin and the new pin is fully explained by
> the diff between a baseline ref and the working tree.

Recompute each expectation **twice** — once against the tree as of the
baseline, once against the working tree — and rewrite only when the baseline
run reproduces the OLD pin byte for byte. If anything other than your change
had moved the oracle, the baseline would not reproduce the old pin either;
that pin is `stale`, and it is reported rather than written. The refusal is
the feature.

## Steps

1. **Check whether the provenance still resolves before assuming it doesn't.**
   Try the obvious verification first and score it. In round 450 the obvious
   one was "rebuild the mutant from its id and re-run it": **0 of 64** pins
   had an id whose `(file, line, description)` still named a site, because a
   mutant id is a line number plus a generation counter and both move on
   every edit to the mutated file. Score it, publish the number, and only
   then fall back — an unmeasured "that isn't possible" is a guess.
2. **Parse the generated file with a parser, not a regex.** The pinned values
   are `repr()` output full of quotes, backslashes and newlines. Use the
   language's own AST (`ast.parse`, `ts-morph`, `go/ast`) and record each
   pin's assertion LINE RANGE for step 6.
3. **Build the baseline as a tree, not as a stash.** Copy the project, then
   overwrite only the subject package from the ref:
   `git show <ref>:./<path>`. Rewinding the whole repo would also rewind the
   tests, and the question is what the SUBJECT did, not what the repo looked
   like. (`./` matters — a bare path in `git show REF:PATH` resolves from the
   repo root, not your cwd.)
4. **Load both trees in one process, once.** Two package loads for the whole
   run, not two per pin; the loads and the copy are what cost, and neither
   depends on the pin.
5. **Judge, and name the verdicts so a reviewer can act on each.**
   `holds` (nothing to do) / `repin` (moved, baseline reproduces the old pin,
   safe) / `stale` (moved, baseline does NOT reproduce it — refused). Print
   the dotted path of every leaf that moved (`vals.v1`, `out[0]`), not the
   diff: a reviewer needs the SHAPE of the blast radius, and 400 characters
   of rendered text per pin hides it.
6. **Rewrite bottom-up, in the generator's own format.** Sort by descending
   line so an earlier rewrite cannot move a later pin's recorded range, and
   render the line exactly as the generator renders it (same `%r`, same
   indent), so a re-pinned file is byte-identical to a freshly generated one
   and the next real regeneration produces no spurious diff.
7. **Check the diff shape, then the count.** `git diff --stat` on the
   generated file must show exactly N insertions and N deletions for N
   `repin` verdicts, and nothing else. A changed line count means the
   rewriter reformatted something.
8. **Publish the verdict census in the commit message.** `64 pins, holds 53,
   repin 11, stale 0` is the evidence that the update was not `-u`.

## Pitfalls

- **`-u` on a red suite you did not fully diagnose.** The one this exists to
  prevent. Every snapshot tool ships this flag and it cannot distinguish your
  change from a regression your change caused.
- **Deleting the failing tests instead.** Cheaper, looks tidier in review,
  and destroys strictly more than updating them.
- **Believing the docstring's recorded "before" value.** Generators truncate
  it (`docstring_safe(..., 120)`) and mangle it (quotes and backslashes
  replaced so it survives inside a docstring). It is a lossy prefix. Parse it
  if you like; do not compare against it.
- **Proving the wrong inequality.** "The new expectation differs from the
  mutant's RECORDED output" proves nothing: the mutant is the new tree plus a
  mutation, so its behaviour moved with the tree. Either re-run the mutant on
  the CURRENT tree or use the baseline differential — not the recording.
- **A baseline that silently equals the working tree.** Then every pin comes
  back `stale` (baseline reproduces nothing) or `holds`, and the run looks
  fine. Assert that at least one pin is `repin` when you know the change
  moved something, and keep a test that every pin `holds` when the trees
  agree — the two together catch a broken baseline in both directions.
- **Rewriting `stale` pins "while you are in there".** A `stale` pin is a
  second, undeclared change. Land it separately or explain it separately.
- **Nondeterminism read as a change.** A pin whose program uses a clock, a
  hash seed, a temp path or a wall-clock timeout reports `stale` on a busy
  box for reasons that are not about your diff. Re-run before you believe it.

## Verification

Executed from the repo root in round 450.

```bash
# 1. the provenance census — measure the obvious verification's availability
cd harness && python3 -m swe.killerrepin --audit-ids | tail -1
#    -> 64 pin(s): 0 rebuildable by (line, description), 3 more by a UNIQUE
#       description, 61 not rebuildable

# 2. verdicts, no writes; with the trees agreeing every pin must hold
python3 -m swe.killerrepin --check | tail -1
#    -> 64 pin(s) against HEAD: holds 64

# 3. the tool's own suite, including the REFUSAL and the green-tree statement
python3 -m pytest tests/test_swe_killerrepin.py -q      # -> 9 passed

# 4. the diff shape after a real re-pin (step 7), from the repo root
git show --stat f856bae -- languages/whence/tests/test_generated_killers.py
#    -> 22 +++++++++++-----------   (11 insertions, 11 deletions)
```

Step 2 returning anything other than `holds 64` on a clean tree means the
generated file and the subject have drifted for a reason nobody declared —
which is the same alarm, one round later.
